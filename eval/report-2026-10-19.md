### Tags + SubQ against the reference RAG with the LLM judge (2026-10-19, partial)

`npm run bench:compare -- --runs 1` with drafts, on `feature/E7-12-show-benchmark-runs-in-earlier-runs`. The configuration is the one the POC's goal is about: tag search plus a small judge against a regular RAG with an LLM judge.

- **Main flow:** tag search (roaring), the LLM query translator, and `RERANKER=subq` (`subq-snap-preview`, `JUDGE_THRESHOLD` 0.6).
- **Reference RAG:** dense search (bge-m3 int8) and the LLM judge (Haiku, threshold 0.8).
- **Both flows:** `RERANK_TOP_K` 8, the judge cache off, and every LLM role on Haiku through the Claude Code subscription (`LLM_PROVIDER=claude-code`). The judge timeouts were raised to 180 s per chunk and 900 s in total (`JUDGE_CHUNK_TIMEOUT_MS`, `JUDGE_TOTAL_TIMEOUT_MS`), so the LLM judge could finish.

**The run did not finish.** Claude Code stopped it after 13 of the 20 queries (anst-01 to anst-10, nda-01 to nda-03), because the 8 GB machine ran out of memory (swap nearly full). The cause was bge-m3 and up to 8 parallel `claude -p` judge processes. The table above therefore has no row for this run. The figures below come from the run log (`logs/runs.jsonl`, `source: "bench"`, E7-12), which has each flow run's timings and counts. Precision and recall cannot be computed from the log, because it keeps no chunk ids, so they are missing. Source accuracy is the mean of the per-query values, not the pooled ratio the table uses.

- **With a small judge, the main flow has its sources first, every time.** In all 13 queries the main flow knew its sources before the reference RAG did: a median of 32.0 s sooner, and 24.6 s sooner counting the query translation. The judge decides it. SubQ judged 30 candidates in 1.8 s; the LLM judge took 32.7 s. E7-9 showed that with the same judge the two flows tie (26.5 against 26.7 s). The speed claim in `Constitution/Requirements-and-goal.md` therefore holds once the judge is small, not because of the search.
- **The translation is now the main flow's largest wait before its sources.** At 8.5 s (p90 32.5 s through `claude -p`), it is four times the search and judge together. SubQ as translator (E9-1: about 7× faster, but lower candidate recall) or JEV is the lever left.
- **The drafts are about as good, as far as this run can tell.** Both flows wrote a draft for every query. The main flow's references were valid somewhat more often (0.956 against 0.864, mean per query; the reference RAG's nda-03 draft had no valid reference). Without precision and recall, this run says nothing about whether SubQ picks the right chunks. E9-1 measured that on the evaluation set: SubQ ranks best, but its central F1 is lower than the LLM's (0.330 against 0.371).
- **The total is faster too, but less clearly.** Generation takes 30–60 s in both flows and dominates the total. The main flow's drafts took longer (40.9 against 32.1 s; output tokens are not in the run log), which eats into the 32 s lead.

**Caveats:**

- One run, 13 of 20 queries, and no precision or recall.
- The LLM judge ran through `claude -p` on the subscription. That is slower per call than the API (E7-9 measured 26.6 s for the same 30 candidates), so the judge gap here is probably larger than it would be with `LLM_PROVIDER=anthropic`.
- The machine was under heavy memory pressure, which probably slowed the local steps. Tag search took 151 ms here against 2 ms in E7-9, and embedding took 1.1 s against 49 ms. Those steps are small next to the judge and generation, so the conclusions above do not depend on them.
- SubQ cost at most 0.025 USD; the actual figure is printed only at the end of a run, which this one did not reach.

**To finish the measurement:** run the full set again outside Claude Code's background shell (or with a lower `JUDGE_CONCURRENCY`, at the cost of a slower LLM judge). Then add its table row and precision/recall here.
