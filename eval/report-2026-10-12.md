### First comparison run (2026-10-12, E8-5)

Demo machine (Intel Core i5-8257U, 8 GB), 20 queries, today's unreviewed labels. `llm` is `claude-haiku-5-5` through the Claude Code provider (judge cache on; its latency from a cache-off pass over 5 queries). `jev` was skipped (no `JEV_API_KEY`) and `qwen3` is not implemented. BGE int8 and fp32 are two runs (`RERANKER_DTYPE`).

- **Rerankers.** The LLM judge lifts the ranking most: with `tags`, recall@8 goes from 0.172 to 0.324 and precision@5 to 0.580. BGE helps less (0.172 → 0.232 with `tags`) and barely moves the `bge` and `both` lists, which are already ordered by bge-m3. On this set, the local reranker does not match the LLM judge.
- **Retrievers.** `both` has the highest recall over all candidates before rerank (0.564, against 0.509 for `tags`, 0.473 for `bge` and 0.451 for `fts`), so fusing tags with bge-m3 finds the most relevant chunks for a reranker to work with.
- **Latency.** Reranking 30–40 candidates takes about 27–34 s with the LLM (cache off) and 36–48 s with BGE int8 (57–70 s with fp32). Retrieval is 1 ms for tags and about 0.4–0.5 s for `bge`/`both` (embedding the question).
- **fp32 or int8.** The rule (E8-3): fp32 becomes the default if int8's recall@8 after rerank is more than 0.03 below fp32's. int8 is 0.012 above fp32 with `tags`, 0.008 below with `bge` and 0.022 above with `both`, so **`RERANKER_DTYPE` stays `int8`**; it is also about a third faster.
- **Caveat.** One labeller, labels not yet reviewed (#58), 20 queries: differences of a few hundredths are within noise.

### First run (2026-10-12, E5-4)

Demo machine (Intel Core i5-8257U, 8 GB), all 20 queries × 5 runs, drafts on, through the Claude Code subscription: query translator `claude-haiku-5-5`, generator `claude-sonnet-5-5`; main flow `RETRIEVER=tags`, `RERANKER=bge` int8, top 8; reference RAG bge-m3 int8, top 8.

- **Samples.** The subscription's session limit stopped 14 calls in run 1 and 18 in run 5 (16 query and run pairs per flow). A pair that failed in either flow is left out of both, so each row averages over the same 84 of 100 pairs, covering all 20 queries.
- **Time.** The reference RAG is about 2.4× faster in total (median 29.5 s against 71.8 s). Search itself is not the difference (11 ms for tag search, 360 ms for embedding and the vector scan); the main flow's extra time is the BGE rerank (median 37.0 s) plus query translation. Generation takes about the same in both (28–29 s).
- **Relevance.** The main flow sends better chunks: precision 0.398 against 0.302 and recall 0.254 against 0.208. Source accuracy is about equal (0.917 and 0.914).
- **Conclusion.** Tags plus a judge find more relevant sources than a plain RAG, but with BGE as the judge they are not faster. The rerank is the step to cut: E7-5 (#78) measures smaller local rerankers for that.
- **Caveat.** One labeller, labels not yet reviewed (#79), 20 queries; the session-limit gaps fall in runs 1 and 5 only.
