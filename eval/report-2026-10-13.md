### Small reranker (2026-10-13, E7-5)

Demo machine (Intel Core i5-8257U, 8 GB), 20 queries, today's unreviewed labels (#79). `minilm` is mMiniLM-L12 (`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`, int8, AVX2 export), `bge` is bge-reranker-v2-m3 int8. Query translation for `tags` and `both` through the Claude Code subscription.

- **The default rule.** `minilm` replaces `bge` as the default when its recall@8 after rerank is at most 0.03 below BGE's with `tags` and `both`, at a third of BGE's rerank time or less. With `tags`: 0.234 against 0.256 (−0.022), 3.0 s against 27.7 s (9.2× faster). With `both`: 0.211 against 0.230 (−0.019), 4.5 s against 36.6 s (8.2× faster). Both hold, so **`RERANKER` now defaults to `minilm`**.
- **Where a reranker helps.** With `tags`, both rerankers lift the ranking (recall@8 0.175 before; 0.234 with `minilm`, 0.256 with `bge`). With `bge` and `both`, whose lists bge-m3 already orders, neither does: recall@8 before rerank is 0.212 and 0.251, and both rerankers bring it down. E7-4 (#58) weighs the candidate count and `RERANK_TOP_K` against this.
- **Caveat.** One labeller, 20 queries: differences of a few hundredths are within noise.

### Candidate counts (2026-10-13, E7-4)

Demo machine, 20 queries, labels graded by Claude (131 central of 266; the owner's review is #79), reranker `minilm` int8, query translation through the Claude Code subscription. For `tags`, each count's list comes from tag search with `MAX_CANDIDATES` = N; for `both`, from fusion with `RETRIEVE_CANDIDATES` = N over the configured tag search (`MAX_CANDIDATES` 30), as the query flow runs it. Each query's lists are reranked once together, without the cache.

- **The rule.** For each retriever, among the settings whose central recall is at most 0.03 below the old defaults' (`tags` 30 candidates, `both` 40, both top 8), the highest central F1 wins. Within 0.01 of it, the fewest candidates win, and of those the highest central F1.
- **`tags`: stays 30 candidates, top 8.** It has the highest central F1 (0.221); 30 with top 10 (0.215) is the nearest. 20 / top 8 (0.202) loses central recall: 0.238 against 0.269.
- **`both`: 20 candidates, top 12.** Central F1 0.194 against 0.123 at 40 / top 8, and central recall 0.289 against 0.146. The estimated rerank time is 1.8 s instead of 3.5 s. A longer fused list puts more chunks that are only loosely related in front of minilm, and it ranks some of them above the central ones.
- **`RERANK_TOP_K` is shared by the retrievers, so it follows the default retriever `tags` and stays 8.** With `RETRIEVER=both`, `RERANK_TOP_K=12` is the better setting (at top 8, `both` at 20 has central F1 0.172).
- **New defaults:** `MAX_CANDIDATES` stays 30; `RETRIEVE_CANDIDATES` 40 → 20; `RERANK_TOP_K` stays 8. `RETRIEVE_CANDIDATES` also applies to `RETRIEVER=bge`, which the sweep did not cover.
- **Rerank times are estimates:** each query's rerank time per candidate times N, from the one rerank of the union, so they are the same for both retrievers at the same N.
- **Caveat.** One labeller and 20 queries, and the query translation varies between runs (the `tags` rows moved by up to 0.03 in central F1 since the run before), so differences of a few hundredths are within noise.
- **Earlier sweeps the same day measured `both` wrongly** (the first N of a 50-candidate list, then a tag ranking capped at N instead of `MAX_CANDIDATES`). Their rows were removed.

`npm run bench:compare -- --runs 1` with drafts, the default `RERANKER=llm` (Haiku judge, `JUDGE_THRESHOLD` 0.8), judge cache off, every role on Haiku through the Claude Code subscription; 20 queries, no failures. Medians:

### The same judge (2026-10-13, E7-9)

`npm run bench:compare -- --runs 1` with drafts. Both flows now judge their candidates with the same LLM judge: `RERANKER=llm`, Haiku, `JUDGE_THRESHOLD` 0.8, `RERANK_TOP_K` 8, one shared instance. The judge cache was off, and every role ran on Haiku through the Claude Code subscription. The run covered 20 queries with no failures and no unknown judgements. Both flows wrote no draft for the same query (`nda-10`), so the draft measures are over the same 19 pairs. The only intended difference is how the candidates are found: tags (with the full-text fallback) against vectors. Medians:

| Step                                  | Main flow (tags)      | Reference RAG (vectors) | Difference                                     |
| ------------------------------------- | --------------------- | ----------------------- | ---------------------------------------------- |
| Translation                           | 7.4 s                 | –                       | +7.4 s for the main flow                       |
| Search                                | 2 ms                  | 55 ms (49 ms embedding) | 53 ms faster with tags                         |
| Candidates judged                     | 30                    | 30                      | the same                                       |
| Judge                                 | 26.5 s                | 26.6 s                  | the same                                       |
| **Time to sources** (search + judge)  | **26.5 s**            | **26.7 s**              | **0.2 s sooner**; 7.2 s later with translation |
| Generation                            | 39.6 s (7,328 tokens) | 35.3 s (6,740 tokens)   | 5.2 against 5.3 ms per output token            |
| Total                                 | 73.3 s                | 64.0 s                  | 9.3 s slower                                   |
| Precision / recall of the chunks sent | 0.516 / 0.279         | 0.419 / 0.204           | +0.097 / +0.075 for tags                       |
| Source accuracy                       | 0.973                 | 0.954                   | about the same                                 |
| Pairs without a draft                 | 1                     | 1                       | the same query                                 |

- **With the same judge, the two flows have their sources at the same time.** The judge takes 26.5 s in both, since both give it 30 candidates. Tag search beats vector search by 53 ms (2 ms against 55 ms), but that is 0.2 % of the time to sources. The judge decides how fast the sources come, not the search.
- **What tag search costs is the translation.** Counting the 7.4 s LLM call that turns the instruction into tags, the main flow has its sources 7.2 s later than the reference RAG. The total is 9.3 s slower: the translation, plus 4.3 s more generation for longer drafts (7,328 against 6,740 output tokens at the same ~5.3 ms per token).
- **What tag search wins is relevance.** The chunks the main flow sends to the generator have precision 0.516 against 0.419, and recall 0.279 against 0.204. Source accuracy is about the same (0.973 and 0.954). The judge closed most of E7-8's precision gap (the reference RAG went from 0.287 to 0.419), but tags still find better candidates for it.
- **The thesis's speed claim rests on the translation step.** The search itself is faster, but too small to matter next to the LLM steps. JEV (#79) is meant to make the translation and the judge cheap; until then, tags give better sources about 7 s later.

**Differences that remain between the measurements:**

- **The labels favour tags.** `eval:label` showed the tag-search and full-text candidates, and `eval/queries.yaml` was labelled from them. A relevant chunk that only vector search finds is unlabelled and counts against the reference RAG. Part of the relevance gap may be this bias. [#95](https://github.com/bjornpetersson1/RAG-JEV-LLM/issues/95) (E7-10) labels the dense candidates.
- **The translation step only the main flow has.** It is left out of the time to sources and given on its own, but it is part of the total and of LLM time.
- **Candidates judged.** The reference always gives the judge `MAX_CANDIDATES` (30). Tag search gives up to 30, and full-text search only fills up to `MIN_TAG_CANDIDATES`. Here the median was 30 in both.
- **The embedding step only the reference has** (49 ms, part of its search time).
- **The search text.** The main flow searches with the instruction plus the translated tags, and the template's preset tags for the 6 queries with a template. The reference embeds the instruction alone.
- **Unknown judgements.** The judge's total timeout (`JUDGE_TOTAL_TIMEOUT_MS`, 60 s) could cut one flow more than the other. None did in this run (0 unknown in both).
- **The UI's judge cache.** The UI keeps the cache on, and the reference runs after the main flow with the same question, so chunks both flows found are cache hits for the reference. The timing panel shows each flow's cache hits. This benchmark ran with the cache off.

**Caveat.** This is one run (the requirements ask for five; as in E7-8, one stays within the subscription's limits), and CLI times overstate API times. The run started before two code-review fixes (a draft without text counts as no draft, and `judged` counts the loaded candidates). They change nothing here: both flows wrote exactly the drafts whose judge approved chunks, and the judged medians are the full 30.

Recall is not comparable with E7-9: there are 149 more relevant chunks to find, and the judge still sends at most 8. - **Timing is unchanged.** Both flows judge 30 candidates, so the judge takes the same time (28.0 and 27.9 s) and the sources arrive at the same time. On these labels, tags do not find better candidates for the judge than vectors either; whether vectors find better ones depends on the tag-only candidates still to be reviewed. JEV (#79) is still meant to make the translation and the judge cheap, which is where the speed claim must come from.

**Caveats:**

- **The labels may now lean towards vectors.** Every dense candidate was read in E7-10. The tag-only candidates were read in E5-3 and E7-4, with that day's query translation, and were not read again. A relevant tag candidate that today's translation finds but E5-3's did not would be unlabelled and count against the main flow. Among the dense candidates, E7-10 found 38 relevant chunks that tag or full-text search also lists today but that were not labelled, so there are likely more among the tag-only candidates.
- **One labeller, and the owner's review (#79) is still open.**
- **One run.** The judge could not score 4 of the main flow's candidates (a call failed or a timeout cut it), and the main flow's p90 time to sources is 46 s against 32 s. Differences of a few hundredths in precision are within noise.
- **Different runs.** This run and E7-9's are different runs on different labels. The before-the-judge table above shows the effect of the labels on the same candidates.
